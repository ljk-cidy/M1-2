# 실제 평가 항목 대조 검증

검증일: 2026-10-18 · 대상 저장소: ljk-cidy/M1-2, main

실제 GPT 연동 후속 점검: 잔액 추가 후 요청 2회 모두 200. 요약 주입 결과와 실제 통계 수치 일치, 같은 대화 ID로 후속 질문 처리, Firestore 4개 메시지 원문 일치, 새로고침 후 웹 대화 복원까지 확인했습니다. 이전 잔액 부족 상태는 해소되었습니다.

[코디세이 평가 화면](https://usr.codyssey.kr/daejeon/ev/participation/evalutionParticipationSave)의 동일 미션 ‘5. 평가문항’을 읽고 대조했습니다. 열람한 화면은 다른 제출자의 평가 건이므로 그 제출물·점수·피드백은 본 보고서의 근거가 아닙니다. 사용자 저장소와 로컬 API만 검증 대상으로 삼았으며 평가 입력·저장은 하지 않았습니다.

**현재 전체 PASS를 입증할 수 없습니다.** 주요 미완료 증빙은 Render/Vercel 배포와 작은 화면의 사용성입니다. 설명형 항목은 코드 근거를 정리했지만 본인의 구두 설명 능력은 별도 확인해야 합니다.

## 항목 1 — 실제 서비스 동작

| 평가 기준 요지 | 근거 | 결과 |
| --- | --- | --- |
| 배포 URL 접속 | render.yaml, frontend/vercel.json 존재. README에 실제 배포 URL 없음 | 배포 접속 미검증 |
| Swagger 문서 | 실제 로컬 /docs, /openapi.json 모두 200 | 로컬 확인, 배포 환경 미검증 |
| 웹 데이터 추가→Firestore→목록 반영 | 앞선 UI 검증 및 실데이터 적재·재조회. 현재 목록/요약 102개 일치 | 로컬 근거 확보. 최종 웹 추가 시연 권장 |
| 요약 응답 및 답변에 요약 반영 | 실제 summary 200. 채팅의 시스템 메시지 주입은 모의 SDK 테스트 통과 | 실제 GPT 답변 수치 일치 확인 |
| 대화 저장·목록·불러오기 | 실제 요청 2회 성공, 동일 대화의 4개 메시지 저장, API 상세 원문 일치 및 새로고침 후 웹 복원 확인 | 로컬 실제 저장·복원 확인 |
| 모바일·작은 화면 | 800px 이하 CSS 재배치, 폼 줄바꿈, 표 가로 스크롤 구현 | 360px 폭에서 페이지 가로 넘침 없음, 4개 메시지 복원 표시 확인. 실제 기기 키보드·전체 CRUD 흐름은 추가 확인 필요 |

현재 데이터는 102개(초기 예시 100개 + 그 외 기록 2개), 유효 모델 102개, 날짜 102개입니다. 예시는 10일 반복 패턴이며 실제 관측에서 수집한 기록은 아닙니다. 통계: 총합 428시간, 평균 4.2시간, 표준편차 1.11. 이 숫자는 조회 시점 기준입니다.

## 항목 2 — 구조·스키마·화면 상태 설명

| 평가 기준 요지 | 구현 근거와 설명 | 보완/한계 |
| --- | --- | --- |
| 라우터와 서비스 분리 기준 | routers는 HTTP·검증·저장 흐름, services/analyzer.py는 외부 의존성 없는 통계 계산, config는 연결 설정 | Firestore 접근은 라우터에 남아 있음. Repository 계층이 있다고 설명하면 안 됨 |
| data/conversations 구조 선택 | 시계열은 date/value/memo 문서, 대화는 title/messages 문서로 분리해 목록·CRUD와 대화 복원을 독립 처리 | 사용자별 분리·인덱스 최적화 미구현 |
| Pydantic 요청/응답 설계 | 날짜, 유한한 수치, 역할, 길이, 빈 입력, 알 수 없는 필드 검증. data CRUD는 응답 모델 지정 | chat·대화·summary 응답의 명시적 Pydantic 모델은 없음 |
| 프론트 상태 흐름 | currentConversationId로 대화 선택, busy로 중복 제출·전환 차단. CRUD 성공 후 목록/요약 갱신, 복원 성공 후 메시지 교체 | 오류 표시와 서버 저장 성공 시점 중심으로 설명 가능 |

구조 설명에 필요한 코드 근거는 있습니다. 평가 시 구현자가 왜 이렇게 나눴는지 자신의 말로 설명해야 합니다.

## 항목 3 — 설계 선택의 근거

| 평가 기준 요지 | 설명할 근거 | 한계 |
| --- | --- | --- |
| 컨텍스트 주입을 선택한 이유·장단점 | DB 요약을 시스템 메시지에 제공해 데이터 기반 답변 유도. 원시 데이터 전체 전달보다 작은 입력 | 개별 날짜·월별 상세가 손실되고 정확한 답변을 보장하지 않음 |
| summary API를 분리한 이유 | 프론트 요약 카드와 AI 답변이 같은 calculate_summary를 재사용 | chat은 내부 HTTP 요청 대신 같은 계산 함수를 직접 호출함 |
| 대화 저장 시점과 형태 | GPT가 비어 있지 않은 답변을 반환한 뒤 user/assistant 한 쌍을 저장. 후속 요청은 기존 문서 갱신 | 단일 문서 100개 메시지 제한, 최근 20개만 GPT에 전달. 동시 요청 시 갱신 충돌 대응 미구현 |
| 환경 변수 선택 이유·적용 | 키는 .env/서버 환경, 출처는 ALLOWED_ORIGINS, 모델은 OPENAI_MODEL. Vercel 빌드가 API_BASE_URL을 공개 config.js로 변환 | 로컬 키와 실제 GPT 요청 정상. 배포 적용 증빙 없음 |

설계 이유는 코드와 문서로 설명할 수 있지만, 실제 GPT 동작은 확인했으며, 배포 환경의 동작 증빙은 추가해야 합니다.

## 항목 4 — 운영·보안·변경 대응

| 평가 기준 요지 | 현재 대응 | 한계/변경 방향 |
| --- | --- | --- |
| 콜드스타트 안내·완화 | 첫 요청 지연 안내, 최대 90초 대기, 타임아웃 안내 | 실제 Render 콜드스타트 미검증. 서버를 항상 켜두는 구현은 아님 |
| CORS 발생 이유와 해결 | 프론트/백엔드 origin이 달라 허용 목록 필요. localhost:5500 POST preflight 200 확인 | 실제 Vercel origin 등록과 배포 검증 필요. CORS는 인증 아님 |
| 악성 입력·오염 대응 | Pydantic 필드/역할/길이 검증, DOM textContent 사용, CSV 따옴표·수식 처리, 요약을 명령으로 취급하지 않는 프롬프트 | 인증·사용자 소유권·서버 호출 빈도 제한 없음. 학습 시간에 대한 API의 0~24 범위 제한도 없음 |
| 데이터 증가·최근 30일 기준 변경 | 조회 단계에서 날짜 범위를 제한하고 공용 분석 흐름을 수정한 뒤 API·채팅 양쪽에 적용 | 현재는 전체 stream으로 읽음. Firestore 날짜 쿼리·페이지 처리·요약 캐시와 복합 테스트 필요 |

최근 30일은 기준일과 포함 범위, 데이터 없는 날 처리 방법을 먼저 정해야 합니다. 프론트 표시만 바꾸면 AI가 쓰는 요약과 불일치하므로 공통 데이터 선택 로직을 적용해야 합니다.

## 항목 5 — 보너스

- 표준편차, SVG 그래프, CSV 내보내기, 다크 모드: 코드 및 앞선 로컬 UI 검증 근거 있음.
- Function Calling과 MCP/GPT Actions 연결: 미구현.
- 보너스 점수·PASS/FAIL은 본 보고서에서 확정하지 않습니다.

## 실제 로컬 채팅·대화 복원 증빙

![실제 GPT 대화 복원](live-chat-restored.png)

GPT 호출은 2회로 제한했으며 추가 대화 호출 없이 저장 원문과 복원 결과를 확인했습니다.

## 제출 전 우선순위

1. 로컬 실제 GPT 질문→요약 반영 답변→자동 저장→새로고침 후 대화 복원 검증 완료. 배포에도 키를 설정하고 같은 흐름을 재검증합니다.
2. Render/Vercel 배포 후 프론트·백엔드·Swagger URL, 실제 CORS 적용과 콜드스타트를 확인합니다.
3. 작은 화면에서 데이터 추가·삭제·채팅·대화 복원을 직접 시연하고 증빙을 준비합니다.
4. 실제 채팅, CRUD, 대화 복원 스크린샷을 README에 넣습니다. 모의 응답 이미지는 실제 서비스 증빙으로 제출하지 않습니다.
5. 위 표의 이유와 한계를 구현자가 직접 설명할 수 있도록 준비합니다.

검증 기반: 실제 로컬 API 재조회, 코드 검토, 동작 테스트 8개 통과 결과. 점수 입력·다른 제출물 수정·실데이터 변경·평가 저장은 수행하지 않았습니다.
